# Issue #26 — Steps and Prep evidence

The regular-width cooking cover displays Steps and Prep side by side. Compact width keeps Steps visible and opens Prep in an Ingredients sheet. Both use one persisted cook session. Prep stores servings, checked ingredient IDs, optional equipment text, and preferred pane order in migration `v14_cook_prep`; ingredient quantities derive from the original recipe. Opening Prep does not advance the step or create another timer. Role swapping is available only at regular width.

[Apple's multiple-displays talk](https://developer.apple.com/videos/play/tech-talks/111464/) says new windows cannot be created on the outer display. Its `CameraCaptureAccessory` requires an active camera session and a fullscreen app on the inner display. Cook Console does not start a camera merely to access the outer display. This implementation is a two-pane **inner-display layout**, not simultaneous inner/outer physical displays; the compact sheet is the single-screen fallback. There is no hinge/posture detection.

Local Linux evidence: Swift 6.1.3 `swift test -Xswiftc -warnings-as-errors` passed 218 XCTest cases plus 6 swift-testing cases. `swiftc -parse` passed for the changed Swift files; this is syntax-only and cannot compile SwiftUI/UIKit or execute UI tests. `git diff --check` passed. The iOS build, iPhone simulator UI tests, size-class transitions, and timer notification behavior require macOS CI. No Duo simulator or hardware was available locally; do not infer physical-display behavior from the Linux tests. Native CI results must be read from the PR's Actions run before merge.
